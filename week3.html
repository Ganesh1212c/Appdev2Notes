🖼️What is the frontend?

01

The part of the app the user sees and touches. Keep it thin.

WhyIt decides how the app feels. A slow or confusing frontend ruins a perfectly good backend.

  • Frontend = the user-facing part of the app. UI (User Interface) is what is on screen. UX (User Experience) is how it feels to use.
  • Requirements (must have):
    • Avoid complex logic. Application logic belongs in the backend. The user can open and change frontend code in their browser, so it cannot be trusted.
    • No data storage. The backend and database own the data. The frontend only shows it.
    • Work with stateless HTTP. Every request stands alone, so the frontend must carry or ask for whatever the server needs.
  • Desirable (nice to have):
    • Aesthetically pleasing.
    • Responsive: no lag or latency.
    • Adaptive: fits different screens (phone, tablet, laptop).
From the slides
  • User-facing part of app
    • User Interface (UI) and User Experience (UX)
  • Requirements
    • Avoid complex logic - application logic should be in backend
    • No data storage
    • Work with stateless nature of HTTP
  • Desirable
    • Aesthetically pleasing
    • Responsive - no lag / latency
    • Adaptive - different screens

Quick checkWhere should the main application logic live?

The frontend runs on the user's machine and can be changed by them. Logic and data stay on the server.

🧭Programming styles

02

Imperative: say how, step by step. Declarative: say what you want.

WhyModern frontend frameworks (like Vue, next week) are declarative. This idea is the reason they exist.

  • Imperative: a sequence of actions to reach the final result. Draw the boxes for navigation and main text, fill in the text, wait for clicks. One function per step, then compose the functions.
  • Declarative: you specify the desired result. The compiler or interpreter knows how to achieve it, and function integration is automated.
  • UI = f(state): the layout on the screen is a function of the application state (your build methods are the f). Change the state and the UI follows. (Credit: Flutter docs, “Start thinking declaratively”.)
  • Think taxi: imperative = tell the driver every turn. Declarative = give the address.
  • In imperative code you must remember to update the screen yourself. Forget one place and it shows old data.
From the slides
  • Imperative: sequence of actions to achieve final result
    • Draw boxes for navigation, main text, fill in text, wait for clicks etc.
    • Functions for each step, composition of functions
  • Declarative: specify desired result
    • Compiler / Interpreter knows how to achieve result
    • Function integration automated

Quick checkWhich one describes the declarative style?

Declarative = what, not how. The framework works out the DOM steps for you.

🧠State?

03

State is the system's memory.

WhyMost “it worked a minute ago” bugs are state bugs. Knowing which state lives where is half the job.

  • State: the internal details of the system. Its memory.
  • Reproducibility: given a system state, the system should always respond the same way to the same input.
  • Complexity: any non-trivial application needs internal state. You cannot avoid it, so you manage it.
  • Three levels follow: system state, application state, UI (ephemeral) state. Biggest and most permanent first, smallest and shortest-lived last.
  • Think calculator: the number on the display and the stored memory value are its state.
From the slides

  • Reproducibility

  • Complexity

That is reproducibility: state plus input fully decide the response.

🗄️System state

04

Everything the whole system knows. Huge and complete.

WhyThis is the master copy. The backend and database own it, and a frontend can come and go without changing it.

  • Examples: the complete database of amazon.in or flipkart.com (stock of items, prices, logged-in and registered users).
  • All news articles ever published on toi.com, thehindu.com, bbc.com.
  • All students, courses, marks and certificates for NPTEL.
  • Typically huge, but comprehensive: it covers everything, for everyone.
  • Completely independent of the user interface / frontend. Replace the whole frontend and the system state does not change.

Quick checkWhich of these is system state?

System state covers the whole system and every user. A tab or a theme is far smaller.

👤Application state

05

The system as one user (one session) sees it.

WhyThis is the state the frontend really needs to hold, or to ask the server for: your cart, your settings.

  • Application state: the system as seen by an individual user or session. It includes interactivity and session management.
  • Examples: shopping cart, user preferences, theme; followed news items, recommendations; dashboard displays.
  • It is a personal slice of the system state. Two users share one system but have different application states.
From the slides

Quick checkWhose state is a shopping cart?

A cart belongs to one user in one session, so it is application state.

⏳UI (ephemeral) state

06

The part you actually see and touch. Short-lived.

WhyIt is fine to lose it on a refresh, which is why it is the safest state to keep only in the browser.

  • UI state: the part of the application that is actually seen or interacted with.
  • Ephemeral = “lasting for a very short time” (the term Flutter uses).
  • Examples: loading icons; the currently selected tab in a multi-tab document or page.
  • Rule of thumb: if losing it on refresh is harmless, it is probably UI state.

🔄Application and UI management
07




HTTP forgets. So someone has to remember: the client or the server.


WhyThis choice shapes the whole design: where bugs hide, how fast the app feels, and what the server must store.


  • HTTP is stateless: every request is independent. The server does not remember the one before.
  • So how do client and server share state? Two ways:
  • Client maintains state: the browser keeps the state and sends requests to the server for specific items.
  • Server maintains state: the server keeps the state and only allows the client specific requests.
  • Real apps mix both: the server holds the system state, the client holds the UI state, and application state is shared between them.




Client maintains stateServer maintains state



Who remembersThe browser (JS variables, cookies)The server (sessions, database)


What the client doesSends requests for specific itemsOnly makes the requests the server allows


Good forFast UI: no round trip for small changesControl, security, one source of truth


Watch outThe user can tamper with itMore server work, a request per step

  • How to convey state between client and server?

Quick checkHTTP is stateless. What does that mean?
The server does not remember earlier requests by itself. State has to be carried by the client or stored by the server.






⭕Example: Tic-Tac-Toe
08




Three design questions, answered with state.


WhyOne tiny game shows every idea of the week: state, render and input.


  • What to display on screen? Draw the board from the state: nine cells (X, O or empty), whose turn it is, and the winner if there is one.
  • Who determines the display? A render function of the state: UI = f(state). Change the state and the screen follows.
  • How is user input collected and processed? A click on a cell is an event. The handler checks the move, updates the state, then renders again.
  • Where does the state live? One player on one page: all in the browser. Two players on two computers: the server holds the game state and each browser shows it.
